What is SQL Injection (SQLi)?

SQL Injection is a critical cybersecurity vulnerability where an application takes untrusted user input and concatenates it directly into an SQL database query string without proper separation.

🧠 The Golden Rule of SQL Injection:

SQL injection occurs when the database cannot tell the difference between CODE and DATA. When you concatenate strings, user data with special characters (like ' or --) breaks out of the intended data container and gets compiled into executable database instructions!

Visual Anatomy: How String Concatenation Breaks Boundaries

Step 1

Developer's Intention

query = "SELECT * FROM users WHERE user = '" + input + "' AND pass = '" + pass + "'";

The developer expects input to always be a safe literal string like "bob".

➔
Step 2

Attacker Crafts Payload

input = "admin' --"

The single-quote ' closes the expected data string prematurely. The -- marks the rest as a comment!

➔
Step 3

SQL Engine Parses Modified AST

SELECT * FROM users WHERE user = 'admin' --' AND pass = '...';

The database parser completely ignores the password check. The developer's logic is hijacked!

1️⃣

Tautology Attacks

A tautology is a mathematical statement that is always true (like 1=1 or 'a'='a').

' OR '1'='1

Why it works: In boolean logic, FALSE OR TRUE evaluates to TRUE. Every row in the table satisfies the condition, bypassing authentication or leaking all records.

2️⃣

Comment Truncation

SQL provides comment delimiters (-- for line comments, /* */ for block comments).

admin' --

Why it works: Everything after -- is discarded by the SQL compiler. The AND password = '...' clause vanishes entirely, logging the attacker in as the target without needing the password!

3️⃣

UNION Data Exfiltration

The UNION operator merges rows from two separate SELECT queries into a single combined output set.

' UNION SELECT id, username, password FROM users --

Why it works: An attacker exploits an innocent search box to retrieve passwords, credit cards, or internal API tokens that they do not have authorization to see.

🛡️

The Definitive Solution: Parameterized Queries (Prepared Statements)

Why Prepared Statements are mathematically immune to SQL injection

❌ Dangerous: Dynamic Concatenation

// The query string and user data are parsed together in one step:
String sql = "SELECT * FROM users WHERE user = '" + input + "'";
// If input = "admin' --", the SQL parser sees new commands!
  • Input can alter the Abstract Syntax Tree (AST).
  • Data masquerades as executable commands.
  • Blacklist filtering (replacing quotes) is easily bypassed.

✅ Safe: Prepared Statement (Placeholders)

// 1. Database compiles query structure FIRST:
PreparedStatement stmt = conn.prepareStatement(
    "SELECT * FROM users WHERE user = ? AND pass = ?"
);
// 2. Data is bound separately as pure literals:
stmt.setString(1, input);
stmt.setString(2, password);
  • The SQL query AST is compiled before receiving data.
  • Placeholders ? can ONLY hold data values, never syntax.
  • Even if input is ' OR '1'='1, the DB searches for a user whose literal name is ' OR '1'='1!

💻 Remediation Code: How to Fix SQLi in Every Major Language

Review production-ready code examples comparing vulnerable string concatenation against safe parameterized implementations across languages.

❌ Vulnerable Python Code (String Formatting / F-Strings)
# VULNERABLE: Direct f-string interpolation
import sqlite3

def login_vulnerable(username, password):
    conn = sqlite3.connect("production.db")
    cursor = conn.cursor()
    
    # DANGER: Attacker input directly combined with SQL command!
    sql = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'"
    
    cursor.execute(sql)  # Attacker's quotes alter query structure!
    return cursor.fetchone()
✅ Secure Python Code (Parameterized Placeholders)
# SECURE: Using '?' placeholders with tuple of parameters
import sqlite3

def login_secure(username, password):
    conn = sqlite3.connect("production.db")
    cursor = conn.cursor()
    
    # SAFE: SQL structure is static. Placeholders separate code from data.
    sql = "SELECT * FROM users WHERE username = ? AND password = ?"
    
    # Database driver binds variables as literal strings safely
    cursor.execute(sql, (username, password))
    return cursor.fetchone()
❌ Vulnerable Node.js Code (Template Literals)
// VULNERABLE: Direct template literal concatenation
const express = require('express');
const { Client } = require('pg');

app.post('/api/login', async (req, res) => {
  const { username, password } = req.body;
  
  // DANGER: Injected quotes break out of string literal!
  const query = `SELECT * FROM users WHERE username = '${username}' AND password = '${password}'`;
  
  const result = await db.query(query);
  res.json({ user: result.rows[0] });
});
✅ Secure Node.js Code (Parameterized Query `$1, $2`)
// SECURE: PostgreSQL parameterized query using $1, $2 placeholders
const express = require('express');
const { Client } = require('pg');

app.post('/api/login', async (req, res) => {
  const { username, password } = req.body;
  
  // SAFE: Database treats params array strictly as literal values
  const query = 'SELECT * FROM users WHERE username = $1 AND password = $2';
  
  const result = await db.query(query, [username, password]);
  res.json({ user: result.rows[0] });
});
❌ Vulnerable PHP Code
// VULNERABLE: Direct variable interpolation into query
$user = $_POST['username'];
$pass = $_POST['password'];

// DANGER: Attacker alters query logic
$sql = "SELECT * FROM users WHERE username = '$user' AND password = '$pass'";
$result = $pdo->query($sql);
✅ Secure PHP Code (PDO Prepared Statements)
// SECURE: PDO Prepared Statement with named or positional parameters
$user = $_POST['username'];
$pass = $_POST['password'];

$stmt = $pdo->prepare('SELECT * FROM users WHERE username = :user AND password = :pass');
$stmt->execute([
    'user' => $user,
    'pass' => $pass
]);
$user = $stmt->fetch();
❌ Vulnerable Java Code (Statement Concatenation)
// VULNERABLE: Using java.sql.Statement with string concatenation
Statement statement = connection.createStatement();
String sql = "SELECT * FROM users WHERE username = '" 
             + username + "' AND password = '" + password + "'";
ResultSet rs = statement.executeQuery(sql); // Flawed!
✅ Secure Java Code (PreparedStatement)
// SECURE: Using java.sql.PreparedStatement
String sql = "SELECT * FROM users WHERE username = ? AND password = ?";
PreparedStatement ps = connection.prepareStatement(sql);
ps.setString(1, username);
ps.setString(2, password);
ResultSet rs = ps.executeQuery(); // Completely immune to SQLi!
❌ Vulnerable C# Code (String Interpolation)
// VULNERABLE: String interpolation with SqlCommand
string sql = $"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'";
SqlCommand cmd = new SqlCommand(sql, conn);
SqlDataReader reader = cmd.ExecuteReader();
✅ Secure C# Code (SqlParameter Collection)
// SECURE: Using Parameters.AddWithValue or SqlParameter
string sql = "SELECT * FROM users WHERE username = @Username AND password = @Password";
SqlCommand cmd = new SqlCommand(sql, conn);
cmd.Parameters.Add("@Username", SqlDbType.VarChar, 50).Value = username;
cmd.Parameters.Add("@Password", SqlDbType.VarChar, 100).Value = password;
SqlDataReader reader = cmd.ExecuteReader();
❌ Vulnerable Go Code (fmt.Sprintf)
// VULNERABLE: fmt.Sprintf query generation
query := fmt.Sprintf("SELECT * FROM users WHERE username = '%s' AND password = '%s'", username, password)
row := db.QueryRow(query) // Injected characters execute as SQL!
✅ Secure Go Code (database/sql parameter binding)
// SECURE: database/sql QueryRow parameter binding
query := "SELECT * FROM users WHERE username = ? AND password = ?"
row := db.QueryRow(query, username, password) // Safe parameter binding

🛡️ Defense-in-Depth Principles

1

Prepared Statements First

Parameterized queries are the primary, non-negotiable defense. Never rely on manual escaping or regular expressions as your primary barrier.

2

Principle of Least Privilege

Ensure your web app database user has only minimum required permissions (e.g. read/write to specific tables, no DROP TABLE or administrative rights).

3

Hash Passwords Securely

Never store plaintext passwords in a production database. Always use modern salted hashing algorithms like Argon2id or bcrypt.

4

Input Validation (Allowlists)

Validate that usernames conform to alphanumeric character sets and reasonable length limits before sending them to any database layer.
